# silverware-libraries: context for working on this repo

**Silverware**: a collection of plugins (SilverBullet libraries) for [SilverBullet](https://silverbullet.md), installed straight from this repository (`REPO.md` lists them). Each plugin is a folder `silverware-<name>/` (its library page `silverware-<name>.md`, the built `silverware-<name>.js`, `src/`, `silverware-table/ui-tests/`), shown as **Silverware <Name>** (its commands `Silverware <Name>: …`), its settings and Space Lua API under `silverware.<name>` (one global `silverware` the plugins share: `silverware = silverware or {}`, then their field; `config.define("silverware.<name>", …)`: SilverBullet's config splits a dotted key into nested objects, verified in its `client/config.ts`), its CSS classes, data attributes and CSS variables under a prefix of its own. The scripts (build, deploy) list the plugins; vitest, tsc and Playwright find every plugin folder's tests. Renamed from Table Plus (`tablePlus.*`, `tp-`, the repository `silverbullet-libraries`) on 2026-10-22, without keeping the old names: a space using it changes its CONFIG, its scripts (`tablePlus.define…`) and its themes (`data-tp-theme`, `--tp-*`).

The one plugin so far is **Silverware Table** (`silverware-table/`, prefix `swt-`): interactive markdown tables (in-place editing, sorting, filtering, rows and columns, pinning, formulas, column types, copy and paste with spreadsheets). The user-facing documentation is the library page [silverware-table/silverware-table.md](silverware-table/silverware-table.md); this file is the context behind it: how the code is built, what was verified about SilverBullet, and why things are the way they are.

## Commands

```
npm install
npm run build        # bundle silverware-table/src/index.ts into silverware-table/silverware-table.js
npm run verify       # before a commit: tsc (with unused locals), vitest, and the bundle matches src/ (check-build)
npm test             # vitest (unit tests and jsdom UI tests)
npm run test:ui:install  # once: Playwright's Chromium (the version it pins), which the UI tests run in
npm run test:ui      # Playwright: interactions in its Chromium against the playground, which it starts on port 8010
npm run test:ui:open # the same in Playwright's window: tests picked and run one by one, each step's page to look at
npm run check        # tsc
npm run playground   # http://localhost:8000/: Silverware Table without SilverBullet, on mock data
npm run deploy -- <space folder>   # copy the library into a local space
```

## Working rules

- **Rebuild before every commit**: `silverware-table/silverware-table.js` is committed, because SilverBullet installs it from the repo and runs no build. A commit with `src/` changes and a stale `.js` ships the old code. `npm run check-build` (part of `npm run verify`) fails on a stale bundle.
- **Commit messages**: [Conventional Commits](https://www.conventionalcommits.org), one line `<type>(<scope>): <description>`, no body, **no AI co-author trailer**. One feature or fix per commit.
  - Types: `feat` (something new for the user), `fix` (a bug), `refactor` (no change in behaviour), `perf`, `test`, `docs` (the library page, README, this file), `build` (bundling, scripts, dependencies), `chore`, `style` (formatting only).
  - Scope: the plugin (`table` for Silverware Table; a new plugin by its name), `playground`, or none for the repository as a whole (`build: …`).
  - A change that breaks what a space has (settings, the Space Lua API, a theme's selectors or variables, stored markdown) is marked `!`: `feat(table)!: …`.
  - The description in the imperative, lowercase, no period: `fix(table): keep the toolbar over a table rendered anew`.
  - History before 2026-10-22 uses `Table Plus: …` / `Silverware: …` subjects.
- **Commit only when the user says so** ("commit"); until then changes stay in the working copy. Never push without being asked; never push to `main` directly unless asked. A change spanning several fixes is split into commits, each with `silverware-table.js` built from its own changes.
- The conversation with the user is in Czech; everything in the repository (code, comments, docs, commit messages) is English.
- **A fix goes where it belongs**: the core gets generic mechanisms only (it knows no module by name, nor a module's classes or settings), a module's fix stays in the module. Features read rows through the host (`bodyRows`, `shownRows`, `cellAt`), never by querying the table's DOM.
- **What SilverBullet runs is not touched for the playground**: the benchmark measures from outside (playground/profile.ts wraps methods); no measuring, flags or checks for it in `src/`.
- Do not write files of a SilverBullet space on disk while SilverBullet has it open: it keeps its copy and writes a sync conflict into the page (it did, in CONFIG.md). Change pages through SilverBullet (its UI, a Silverware Table command).
- Every commit: `npm run build`, then `npm run verify` passes (tsc with `--noUnusedLocals`, which tsconfig does not enforce; vitest; the bundle checked against `src/`).
- A change to how tables are used (pointer, touch, menus, what survives a write) gets a scenario in `silverware-table/ui-tests/`, and `npm run test:ui` passes before its commit (not part of `verify`: it needs a browser and takes longer).
- Code style: match the surrounding code. Comments explain why, in full sentences or fragments; user-facing strings and docs are English. The library page is written for users: plain, specific, no internals.
- Line endings are LF (`.gitattributes`); editors on Windows may write CRLF into the working copy, git normalizes on commit.
- When editing files from a shell on this machine, heredocs mangle backslashes: write scripts to a file (or use an editor tool) when the text has `\`.

## Architecture

- **The controller is the host.** Features never touch its internals; the modules of `features/` get a `ModelHost` (`core/feature.ts`: tables by key, cells by markdown row and column, no element; docs/silverware-table-isolation.md), the adapter's modules a `TableHost` (with the rendering), and they implement optional hooks: `start/stop`, `selectionChanged` (the selection module changed the cells selected), `cellMenu` (the cell menu asked for on a cell: a feature opens its own instead; the grips' for rows or columns selected whole, by the point, and a header's: its column's menu, the column selected, unless it is in a selection of several cells; a cell being edited saved first, the menu opened again on the table rendered anew: `menuAgain`; a right click whose press saved an edit lands on a table not enhanced yet: the controller waits for it, then opens the menu at the point), `lineMenuEntries` (first in a row's or column's menu, for the lines its grip acts on: the paste module's Copy, Cut, Paste), `cellMenuOpened` (a feature's own menu closes: a tap opening the cell menu sends no mouse event it would close on), `pointMenu` (an adapter module's own menu at a point in no table's cell, what opens it or none, asked as a right click comes and as a touch starts, so a long press is watched only where one opens: the sheet's empty cells), `scrollBox` (the box a module scrolls its tables and cells in: autoscroll moves it), `selectionLeaves` (an arrow, or Ctrl+arrow, at the table's edge, away from it, on a cell selected alone or (Ctrl+arrow) edited: what selects or edits the cell past it, where a feature has one: the sheet view's empty cells; the editor asks before it closes), `fillCell` (a feature's copy of its cell for another cell: formulas, for AutoFill), `addressFrame` (`host.addressFrame(info)`: the addresses a table's cells have where a feature lays it out on a grid of its own, the sheet, and the table's place there (`origin`, `cellAt`, `placeProblem`, `previewPlace`, `moveTo`: the selection module drags a whole table selected by its edge through it); the formulas module translates the editor's text, titles, outlines, pointing and dragging through it, `framedOut`/`framedIn`, a formula it cannot show so stays as stored for that edit: `unframed`), `mouseDown` (any button, first), `beforeMouseDown`, `beforeCellPress` (true: taken, e.g. pointing), `afterCellPress`, `keyDown`, `enhanced`, `decorate`, `toolbarButtons`, `columnMenuEntries` (`columnMenuLeadEntries` before the sorting: the column's type), `menuNaming` (a menu's title named: `TableHost.openTableMenu`), `cellHovered/hoverEnded`, `pointerBusy` (`pick`: a feature picking a place with the next press gets the keys first, Move table…), `layoutChanged`, `beforeWrite`, and the editor hooks `editorText`, `editorOpened`, `editorKeyDown`, `editorValue`, `editorClosed`. Features get events in the order of the list in the controller's constructor (Sticky first, so the header moves before what points at it; ColumnTypes after Formulas, so formula results get formatted; AutoFill before Selection, so Esc during a fill cancels it and the selection stays).
- **Every write is one `editor.replaceRange`** (one undo step; a table's writes one after the other, each waiting for the one before; a write from the table as it was rendered before its last writes, not rendered anew yet, writes it as those left it in the markdown, the pins it sets moved by theirs: `writtenAs`/`writeTarget` in the controller, else a + pressed twice before SilverBullet rendered found the table changed; nothing waits for the rendering, which a table far out of view never gets): `write(widget, change, { focus, rowMap, columnMap, pins })` re-reads the table, applies `change`, then the **write steps** (the features' `writeStep` (formulas: calculated cells for new rows, references follow moved rows/columns, recalculation), then the core's `metadataAfterEdit`: every attribute of a column follows its column, pins), formats (autoFormat setting) and writes. `rowMap`/`columnMap` say where each row (markdown index, header 0) or column went; undefined means deleted. A row no old row maps to is new.
- **Viewing never writes.** Sorting and filtering are views unless the metadata setting stores them. Stale formula results are offered as *Recalculate*, not rewritten on view.
- **Sorting, filtering and copying use `cellValue(cell)`**: `data-swt-value` (set by column types) or the shown text.
- **Settings** (`bridge.ts` SETTINGS, `config.define` on the library page): whole-table settings are `silverware.table.<setting>`, a core part's `silverware.table.<part>.<setting>` (`editor`, `expressions`), a module's `silverware.table.modules.<module>.<setting>`, so a part is set with one `config.set("silverware.table.editor", { … })` and SilverBullet fills in the defaults left out. The modules (`FEATURE_NAMES`) can be turned off with `silverware.table.modules.<name>.enabled`; the controller reads these once when it starts and creates only the features that are on (a change applies on reload).
- **A module turned off is not loaded at all**: what it stored in tables stays and is not used (filters stored do not hide rows; with formulas off, results stay as written). The core knows no module: it offers generic mechanisms. Rows a feature hides (`hiddenRows`, `hidesRows` for "rearranged"); `columnsMoved` for state by column; `action` for clicks on a feature's `data-swt-action` elements in a table (clicks there reach the controller only); toolbar chips (`place: "chip"`); the cell menu (right click, long press, Menu key): `cellMenuEntries` in groups by `order`, `selectedCells` when the right click is in a selection. A menu's title has a × closing it (`onMenuClose` in core/menu.ts: whoever shows the menu says how, as for Esc). A menu's title names what it is about (`menuNaming`: the table's ⋯ menu, a cell's (a header's: its column), a row's or column's grip menu): a pencil after it turns the title into a field (`MenuNaming` in menu.ts: Enter saves, a refusal shown under the field, Esc leaves it; `clear`: a button under the field saving no name where there is one, *Remove from sheet* (the table's name has none: an empty name does it), not in the danger color as nothing is lost; in the ⋯ menu the × of the sheet's row), the menu closed once saved; `openTableMenu(widget, true)` opens the ⋯ menu with the field (the table's name in the toolbar). Attributes of columns in the metadata row, `<owner>.-c-<column>.<key>` (`core.-c-qty.sort='desc'`, `filters.-c-status.condition='=open\|blocked'`, `-c-qty:2` the second column of that name; metanames.ts): `metadataAfterEdit` keeps every such attribute on its column through renames, moves and deletes whatever it is for (`followColumnMeta`), so data of a module turned off stays right. Writes: `prepareWrite`/`prepareEdit` (async, before the text is read and after the edit: pageLinks reads other pages), `writeStep`, `refusesWrite` (a feature refuses the write, said so: nothing written), `otherTablesWritten` (formulas: tables referring to the edited one, in the same edit; the sheets module: the sheet's widths handed over; a table two features change: the later one gets the earlier one's in `edit.page.tables`). Other pages: the pageLinks module (which reads only while formulas are on: `host.moduleOn`) provides `otherPages()` (`host.otherPages()`), formulas read them through `formulas/page.ts` (`pageTables`; a page not read is `unread`, so formulas referring to it keep their results). *Delete table* (the core's, last in the ⋯ menu: `deleteTable` in the controller) asks first with what the modules say goes with it (`tableDeleteWarning`: formulas of tables referring to it, a sheet whose only table it is) and deletes it with the blank line after it in one edit, the other tables the modules change for it (`otherTablesWritten` with no `after`: formulas recalculated without it, `#REF!`; the sheet's data handed to its next table) in the same edit, edits held for it written off. Names: `columnDeleteWarning` (asked before deleting a column); the names of rows and cells are left out of a duplicated row (the core's: `host.uniqueTags`). A table name two tables of the page have (typed or copied in the markdown; naming refuses it): formulas use the first (`pageTables`), the references of other tables follow only the first's edits (`otherTablesWritten`: an edit of a copy moved them off the table they read), the names module marks each such name `attention` in the toolbar (the row shown whatever the setting) and says it once per name and page visit in a notification that stays until closed (`flash`'s `timeout: 0`, verified in the local SilverBullet; the playground's notifications are at the top as SilverBullet's). Remove metadata strips the metadata row and every hidden tag; its question says whose they are, from the attributes' names (`metadataOwners`: the core's, each module's by its label, a module turned off too).
- **The page's view** (`viewBounds`): CodeMirror's scroller (`.cm-scroller`, below SilverBullet's top bar), also while the page is too short to scroll (`scrollParentOf` then finds nothing, and the window's top would put the toolbar over the top bar), cut to the visual viewport (an on-screen keyboard). The cell editor is revealed again when the view resizes (window, `visualViewport`, `navigator.virtualKeyboard`; `core/touch-keyboard.ts`): on a phone SilverBullet (main) pins `#sb-root` to the area above the keyboard (`client/lib/keyboard_viewport.ts`; viewport meta `interactive-widget=resizes-content`).
- **A table written stays where it was in the view** (not one a feature draws, DRAWN_CLASS: its feature places it, after the core would measure it; `core/anchor.ts`: `set` in `write()`, `keep`/`again` in `enhanceNow`): its top's offset in the scroller is restored once it is rendered anew, then after the cell to edit next is revealed, in the next frames and on the scroller's scroll events, for up to `ANCHOR_MS` or until the user wheels, touches, presses or types. The editor scrolled the page while it measured the new rendering (a long table scrolled down jumped).
- **Long text in cells**: the core's `layOutCells` (in `applyView`, so after any feature replaced a cell's content) puts each body cell's content into `div.swt-cell-content` (Silverware Table's own elements, UI_CLASS, stay outside), an inline block as wide as its text: what modules size and limit. The longText module (`features/longtext.ts`, `silverware.table.modules.longText.{overflow, maxWidth, maxHeight}`) sets the limits (classes swt-long-text, which every rule of its CSS requires, swt-cells-wrap / swt-cells-ellipsis and CSS vars on the widget: wrapped up to the maximum height or cut with an ellipsis) and marks cells whose box is overflowed `swt-cut` (after layout, on window resize, a ResizeObserver on the tables, fonts loaded); off, cells are as SilverBullet shows them, and the expand button shows only for a field that does not fit (the popup and F2 are the cell editor's). A header is always on one line (`layOutHeaderCell` in dom.ts, last in `decorate`): `span.swt-head` (inline-flex, at most the maximum width; a width set by the widths module) holds the name (`.swt-head-name`, cut with an ellipsis) and Silverware Table's inline icons after it (type, filter mark, sort), which always show; elements a feature marks `OUT_OF_LINE_CLASS` (positioned at the cell's edge: the pin mark, the width handle) stay in the cell; the core knows no module's element by name. The field of the cell editor is `CellField` (input | textarea): listeners on it go through `HTMLElement`, as the union loses the events' types.
- **The settings dialog** (`settings.ts`; *Silverware Table settings…* in the ⋯ menu, the *Silverware Table: Settings* command, `index.ts openSettings`): tabs: *General* (groups of `SETTINGS` rows: `label` and `hint`, a switch, a choice from `choices`/`choiceLabels` or a number), then one per kind of module (`MODULE_CATEGORIES`, each module declaring its own in `MODULE_CATEGORY`, a record over every module so a new one cannot leave it out; `moduleTabs`), each module's `MODULE_LABELS` name, `MODULE_DESCRIPTIONS`, a switch, its own settings under it while it is on; the tabs one row scrolled sideways where the dialog is narrower (a phone), the one picked scrolled into it; `dialogKeys` (a test requires every setting in it); for every table (it says so). Its keys stay in it (the controller's key handler leaves them, Tab wraps, Esc asks where changes would be lost). It reads the configuration when it opens and changes nothing until Save: then `controller.saveSettings` writes what changed, each value as it is (the default too: the value shown may come from another `config.set`, which the managed block, coming last, overrides; a `readPage` failure other than a missing page writes nothing) with `bridge.saveSettings` (the playground's store) or into SilverBullet's CONFIG page, the Configuration Manager's managed block (`configpage.ts withConfigSettings`: only Silverware Table's `config.set` lines, every other line kept, the block added or removed as needed; verified against `plugs/configuration-manager`), saved by the library page's Lua `saveConfigPage` as the Configuration Manager does (writePage, sync, index, `editor.reloadConfigAndCommands`). One source: Ctrl-, shows what the dialog wrote and the reverse. A module turned on or off: *Save and reload* (`bridge.reloadUI`, `editor.reloadUI`), as modules are created when Silverware Table starts. Without a way to save (no `saveConfigPage`/`readPage` nor `saveSettings`) it only shows them.
- **Rows out of the document**: the core keeps each table's rows as SilverBullet rendered them (`TableRows.renderedRows` in `core/rows.ts`, from its MutationObserver callback, before the browser lays the table out: `tableAdded` to the features), so `bodyRows`, `shownRows` (the display order the view last placed) and `cellAt` have every row whether it is in the document or not; features read rows through them, never `table.querySelectorAll("tr…")`, and do not measure a row out of the document (`isConnected`): `rowNeeded` puts it back first (the cell editor, the selection), `rowsAttached` tells them rows came back (longText checks their cut cells), `holdInDocument` keeps one there (a dragged row). A feature may place the shown body rows itself (`placeRows`): the largeTables module.
- **Large tables** (the playground's benchmark measures them): the browser's layout of a table of thousands of cells is the cost to avoid paying more than once per change. Hooks that run on every view (`decorate`, `viewApplied`, `toolbarButtons`) touch only the cells they change (no style reset on every cell), read layout or computed styles before writing, not between writes, and measure nothing that can wait: the toolbar is built at once but placed in the next frame after a change (`Toolbar.place`). `parseTable` keeps the last tables parsed (they are immutable), so parts reading `info.source` again cost nothing; column types share their `Intl` formatters (`columntypes/format.ts`).
- **SilverBullet's table under a drawn one** (the sheet's, DRAWN_CLASS, standing for its key): rendered anew by a write, it is only registered and the features told (`enhanced`: the sheet follows the page by it), not decorated nor viewed (`covered` in the controller: each write laid both out, 400 rows on the sheet 210 → 160 ms in the playground); once the drawn one is gone (`windowChanged`, the board ended), it is shown as itself (`showEnhanced`), and so is SilverBullet's table of every key a drawn one stood for (`drawnKeys`), rendered anew meanwhile or not: what features placed in the table standing for the key (the width handles of the table the sheet view was opened from) was in the drawn one.
- **Rendered tables are SilverBullet's.** Silverware Table decorates the DOM SilverBullet rendered and matches it to the markdown by position (`data-pos`) and shape. Everything assumed about SilverBullet's DOM lives in `dom.ts`.
- **Esc during a drag** that Esc cancels (`host.drag` with `escape`) is the drag's: the controller routes it to no feature meanwhile (a selection would be cleared, the sheet's board closed).
- **What pressed** (`host.pressedWith`, `data-swt-pointer` on `<html>`, set on each pointerdown when it changes): CSS shows the controls for it (the selection's handles after a touch, the fill handle for a mouse) without modules knowing each other. A press taken (a cell menu a touch opened: a long press, a tap on cells selected through `host.openCellMenu`; a feature's: `host.takePress`, AutoFill to…'s cell clicked or tapped) swallows its mouse events after it, its mouseup and click too (`pressTaken()`, ended by the next pointerdown; the click would run the menu item that opened under the finger, follow a link in the cell, sort), which would close the menu or select or edit the cell; a feature that also acts on taps asks `pressTaken()` first (the selection's tap menu). Taps are told by pointer events (short, not moved: a moved touch scrolls), as Chrome fired no mouse events for a tap after a touch drag or a scroll (verified in its touch emulation). A grip's menu closes when the cells selected change otherwise than by its own line selection (it was for those lines).
- **Selecting and editing through the host**: `selectCells`/`selectedCells`/`selectsCells` (a feature that selects: the selection module), `editCell(info, ref, "replace" | "select")` (open a cell's editor from the keyboard), `saveEditing` (close the editor saving, as leaving it does: what a feature holds stays held), `editBeyond(widget, info, at, td)` (a cell past the table's last row or column, shown by the caller's td: Enter or Tab saves it with the table grown to hold it in one write (`claims` in WriteOptions: the rows and columns added take the empty cells there, as a paste over the edge does; inserted ones are not claimed), `growTo` in structure.ts: rows above those pinned to the bottom, named columns left of those pinned right; nothing written while it is empty; no moving from it, no popup, no lazy holding), `takeEditor` (close the editor, its value saved in the write the caller makes: a paste), `editBeyond`'s `place` (the caller writes what was typed, as typed, no feature making anything of it: the sheet's new table), `insertTable` (a new table into the page after another, one edit, through `beforeWrite`). The editor knows no selection: Esc and Ctrl+Shift+arrows call `selectCells` when `selectsCells()`.
- **Edits held instead of written** (the lazy module): the cell editor asks `holdCellEdit` before writing a body cell (a header's name is written at once); a feature that holds edits gives them through `pendingEdits(info)` (`apply` to a table, `written` once in the page). `write()` applies them to the table it read before its change, so any write takes them along and rows and columns stay in step; `tableOf(info)` is the table with them (what the cell editor starts from). `pageLoaded` (the library page's `editor:pageLoaded` listener, `index.ts pageLoaded`): another page is in the editor, so what was held for the page left goes into its file, never into the editor.
- **Floating controls** (toolbar, grips, the +, menus, panels) are `.swt-floating` elements in `body`, shown with `.swt-visible`; the core makes them (`floating`, `panel`, `floatingMenu`) and keeps which it made (`isFloating`: a press or hover there is on Silverware Table's controls, not the page), so modules declare nothing and make none apart (isolation.test.ts). Hidden with `display: none !important`: themes set `display` on every `button` with `!important` (e.g. Tiniri), which left grips and the + stuck in view.
- **The + on borders** (`core/insert.ts`: `show`, `at`, `inBand`): shown for mouse and pen hover in a band left of the table / above the header (in a lane of its own beside the grips, left of the row grips or above the column grips, on the border nearest the pointer, none over a grip: `INSERT_LANE_*`; the toolbar keeps `BAR_CLEAR` left of the table's right edge, clear of the + there); quiet + buttons under the last row and right of the last column (`quietMarks`, `swt-quiet`, lit up under the pointer) show while a cell of it is edited, hovered or selected (`quietTarget`; hovers go through `cellHovered`, the selection module calls `selectionChanged`), also with the pointer away from the table, and give way to a + the pointer brings up on the same axis; a press on the + or in that band is taken on `mousedown` (it inserts if a + shows), because SilverBullet's table widget moves the cursor into the table on a click (markdown shown). The `mouseup`/`click` ending a press that inserted is swallowed (`endsInsertingPress`): the table rendered anew puts something else under the pointer (a link it would follow). Rows and columns scrolled under what is held over them (the header held at the top, pinned rows and columns: `heldBounds`) get no grip, their borders no +: the floating controls are in `body`, so CSS cannot put the held header over them. Recomputed under the pointer when the page scrolls (`followPointer`), hidden when the pointer leaves the window. While a grip menu is open (`pointerBusy() === "menu"`) the grips keep following the pointer in that table and no + shows.

## What was verified in SilverBullet (by probe pages)

Probes were pages with a test table and a one-line Lua expression listing the index, e.g.
`${(function() local p = editor.getCurrentPage() local out = {} for _, row in ipairs(query[[from index.tag "table" where page == p order by pos]]) do … end … end)()}`.
A new `space-lua` block on a page is not active until Space Lua is reloaded; an inline `${(function() … end)()}` needs no reload.

- **Column keys** in the index: `cleanHeaderFieldName` in `plugs/index/table.ts`: `str.replace(/[\W_]+/g, "_").toLowerCase()`, where `\W` is ASCII-only, so letters with diacritics become `_` (`Množství` → `mno_stv_`). **Hashtags in a header are left out** (`Price #euro` → `price`, `#stars Rating` → `rating`). `columns.ts` mirrors both.
- **Hashtags in a header tag neither the rows (`tags` stays empty) nor the page** (no tag objects).
- **Hashtags render** as `<a class="hashtag sb-hashtag" data-tag-name="…" data-ref="…">#…</a>` (`client/markdown_renderer/markdown_render.ts`).
- **`<meta …>` in a table cell is not shown** (any position, self-closing, single quotes, with `\|`); an HTML comment *is* shown. **A `>` inside a value ends the tag** (in quotes or apostrophes alike: `x <meta note='a > b'>` showed as text, 2026-10-22), as HTML would not: values write it `&gt;`. Values in apostrophes with quotes and `&gt;` inside (`<meta formulas.f='=IF(1&gt;0, "big", "small")'>`, `<meta note='say "hi" &gt; bye'>`) are hidden, two tags in a cell too (verified the same day). The index stores the **raw cell text** including the `<meta>` tag, with `\|` still escaped.
- **Empty cells** are indexed with an empty value (the key is present).
- MdTableRender hides header hashtags with JS (`display: none`), which flickered while tables rendered; Silverware Table hides type hashtags with CSS injected at load.
- **On a phone SilverBullet scrolls to its editor's cursor** whenever its editor counts as focused (`contentDOM.contains(document.activeElement)`, true for a cell editor's field, which is in the content) and the on-screen keyboard shows or goes or the focus moves (`client/components/keyboard_bar.tsx`, seen in a log on Android: CodeMirror's `scrollRectIntoView` setting the scroller's `scrollTop`). SilverBullet also focuses its editor when a page opens. So Silverware Table takes the editor's focus on a touch in a table, does not hand it back after a touch, and scrolls the cell being edited back for a moment after its editor opens or the view resizes (ended by a touch, wheel or press). All of it is in `core/touch-keyboard.ts`, kept apart as a workaround, to go once SilverBullet behaves otherwise.
- **Which tables are in the DOM** (2026-10-22, SilverBullet's source and a probe of CodeMirror 6 alone in Chrome, not in a live SilverBullet): SilverBullet makes a block widget for every table of the page (`client/codemirror/syntax/table.ts`: a `StateField` over the whole syntax tree; none where the cursor is in the table, which shows its markdown), but CodeMirror puts into the DOM only the blocks in its viewport: the part of the page in view plus about 1000 px (`VP.Margin` in `@codemirror/view` viewstate.ts, split above and below; up to 2000 px before it is computed again), and the blocks at the selection's anchor and head. A table far from the part in view is not in the DOM; a table laid over the window (position fixed) is removed too once the page under it scrolls far enough (its place in the text counts, not where it shows), and made anew when it is back in the viewport. One table is drawn whole however tall (one block). So tables shown together (the sheet's variant A) must lie within about the view's height + 1000 px of the page, text between them included: some 40 to 50 rows of 40 px on a laptop. A cursor put into a far table would have it drawn, but SilverBullet shows a table with the cursor in it as markdown. Not verified: what height CodeMirror counts for a widget laid over the window.
- **Space Lua blocks are in the index** (`plugs/index/space_lua.ts`; queried live on 2026-10-22): `index.tag "space-lua"` gives each `space-lua` block with `ref` `Page@position` and `script` (its text), no `page` field; queried from the library page's Lua while Space Lua loads (the API block, as a definition is refused), it has every block. So a refused definition names the pages whose blocks call that API (`callers` in the library page's Lua); the definitions themselves do not say where they come from. The notification stays until closed and has a button per page (at most three) going to the block: `editor.flashNotification(message, type, { timeout = 0, actions = { { name, run } } })`, the options in `client/plugos/syscalls/editor.ts` of SilverBullet's main (verified in the local build; a release before them would ignore the options and close it as any other).
- **Markdown rendered as SilverBullet's table widget renders it** (2026-10-22, probed in the local build, 2.12.1 of main): the widget uses `renderMarkdownInto` with the live context (internal); `markdown.renderToDom(md)` (Space Lua only) gives a live DOM of the whole table with every cell the same as the widget's (`${…}` evaluated live, hashtags, links, `<meta>` kept), only `data-pos` missing, 14 ms for 100 rows; `markdown.markdownToHtml(md, { expand = true })` the same as static HTML (6 ms; without `expand`, `${…}` stays as source). A click on a link or hashtag in that DOM loads the window anew: the widget's handlers are internal (`attachWidgetEventHandlers`), so whatever shows such a DOM routes the clicks to `editor.navigate` itself. Both came with SilverBullet's commit `1dd7556f` (2026-10-10); the release that has them is not verified. Details and the decision for a sheet (cells, not tables, as static HTML): docs/silverware-table-sheets.md, *Cells of a table the sheet draws*.
- **A click on a table widget shows its markdown**: `client/codemirror/syntax/table.ts` listens for `click` on the widget and dispatches a selection at the target's `data-pos` (else the widget's start). Any click that reaches the widget (not stopped by the controller's capture handlers) opens the markdown.

## Design decisions (and why)

### Modules and their data (decided 2026-10-23; the plan and its status: docs/silverware-table-metadata-plan.md)
- **What a module stores in a table goes through its host, and only its own.** The core creates the modules, so it gives each its own host, decorated with that module's identity (its `FeatureName`, lowercased): a module never says who it is, and cannot write as another. The core makes every attribute's name: `<module>.<key>`, a column's `<module>.-c-<column>[:n].<key>` (a marker segment `-x-`, which no column key, module id or key starts with; `-c-` a column, room for others), the core's own `core.<key>`; the module gives only its key and value (`host.setMeta`, `host.getMeta`). The metadata row carries `core.table`, by which the parser tells it from a last row whose one cell holds only a tag, whatever else it has. What the core needs to understand (a column's place, names of tables, columns, rows and cells: `core.name`, `core.n`, `core.cn`) is the core's, read and written through host functions, not a module's data other modules reach into.
- **Domain code (pure, no host) never reads or writes metadata itself.** The module that has the host hands the domain what it needs, in the context it already passes: data built through the host (the formulas' `TableSource`, names of tables and cells looked up by the module) or functions (`getFormula`/`setFormula` made of `host.getCellTag`/`withCellTag`). Not module-level state set at start: dependencies stay visible and nothing depends on the order of starting.
- **A module uses another's data only through an API that one offers** through the host (offered by the provider, asked for by its name; undefined while it is off, which then behaves as "no such data", as for any module turned off). Not by reading its attributes, and not through shared state of a domain.
- **A rule that depends on the state before the whole change belongs to the core's write step**, where the table before, the result of every step and the rows' and columns' maps are together (one write: the steps only transform the model, `replaceRange` writes once). Nested domain code cannot tell editing an attribute from making one: the editor, a paste or a step before may have put it there in the same change. A check at the call is right only where the call has what decides (a table attribute: whether the table has it). So with the metadata setting off: an attribute the table has may change or go, none is added (the core's own too: sorting, pins); a cell's tag passes where the cell had that attribute before the change, or a cell of the table had it with that value (a calculated column's rows, a cell moved across columns), else the core's write step takes it off the cell (its text stays) and says so; the core's own following (columns renamed, moved, deleted; tags with their cells) and Remove metadata always pass. Data handed to another table (a sheet's) is a new attribute like any other.
- **The isolation test checks imports only** (meta.ts's writers and readers out of modules): a guard against calling them by mistake, not an enforcement, as a module could keep data anywhere. Later the modules could get a table model without the raw `meta`; not now.

### Formulas (`formulas/`, `features/formulas.ts`)
- Stored in the cell as the **result plus a hidden `<meta formulas.f='=…'>`**: every renderer and the index see a value; `<meta>` is invisible (verified). Chosen over storing formulas in the metadata row, because a formula addressed by cell position there could, after an edit outside Silverware Table, overwrite a value typed by hand.
- **New formulas need the Store table metadata setting** (they are metadata); with it off a typed formula is saved as text, existing ones keep working (also as calculated columns).
- References: `A1` = first body row (header not counted, as MdTableSheet does), ranges, `[name]` (whole column, without cells whose formulas refer to that whole column: totals), `[@name]` (this row), `[name:2]` for duplicate names. `$` fixes a cell's column or row (`$A$1`, `A$1`, `$A1`, a range's edges each: `Fixed` in references.ts, read by `parseCellName`/`areaOf`; the tokenizer takes a cell with `$` as one name token, as `A1`): it matters only where a formula is filled into other cells (AutoFill); edits of the table move fixed references with their cells as the others, their `$` kept (`followedReference`), as Excel does. F4 in a formula (only there: a text with B2 in it is left alone) cycles the reference at the caret (`cycleFixed`: A1, $A$1, A$1, $A1, a range's ends alike), the reference just pointed at staying the one pointing again replaces; a reference outline dragged or resized keeps its `$` (`dragReference`); a click right before a reference with `$` does not insert one into it (`referenceSlot`); Excel's file gets the `$` as written. Column references are written by **SilverBullet's column key** (`[unit_price]`), the same key a query uses; any spelling with the same key matches.
- Edits made with Silverware Table shift references (rows/columns inserted, deleted, moved, sorted into the markdown, columns renamed); `#REF!` for deleted cells. Edits made in the markdown do not.
- **Other tables**: a table is named in its metadata row (`<meta core.table core.name='prices'>`, its name the title of the table's ⋯ menu (Table without one; while Shift is held in the toolbar too, by the toolbarNames setting), the pencil after it its field, rules in `meta.ts`). Formulas refer to it as `prices!B2`, `prices![price]`, or on another page `[[Page]]prices!B2` (tokens of kind `table`). The evaluator gets a `TableSource` (name, page → Table); a `Book` makes one `Sheet` per table, so other tables' formulas are evaluated too and cycles across tables are `#CYCLE!`. The formulas module builds the source from the page text (`formulas/page.ts` `pageTables`); the pageLinks module caches other pages read with `space.readPage` (re-read for every write that recalculates a table referring to them, and when SilverBullet indexes that page). A write recalculates, in the same edit, the tables that refer to the edited one by name (transitively); their references follow its moved rows/columns, renamed columns and new name (`followTable`). References from other pages do not follow. A page not read (the `pageLinks` module off, or not read yet): `TableSource.unread` makes formulas referring to it keep their stored results (`Book.keepsResult`; an empty one or an error code is an error). `[col]` leaves out the table's total rows (a cell that refers to its own whole column), so columns of a table line up for `XLOOKUP`.
- **Names in cells** (`names.ts`, the core's; `features/names.ts` the naming UI): one hidden tag in a cell, `<meta core.n='…' core.cn='…'>`, kept by the cell editor, paste and Delete. `core.n` names the line the cell heads: in a header the column's name, apart from its header text (named by the pencil in a menu's title: `Feature.menuNaming`; `columns.ts` finds it first, `columnIdOf` writes it, so references and the stored sort use it whatever the header says; verified that SilverBullet leaves `<meta>` out of the column key). In a body cell `core.n` is the row's name (`pear[price]`, in the first cell or wherever a column move took it; unique in the table; bare, `pear` is the row's cells as a range, as `[price]` a column's, all of them: from a formula in that row #CYCLE! (decided 2026-10-24: leaving the formula's own cell out made the same formula give one result in its row and another elsewhere), a cell's name going first: `rowValues` in evaluate.ts; in Excel's file the row's run), and `core.cn` names the cell for formulas, unique in its table (2026-10-22; before, on the page): `vat` is the formula's own table's only, another table's is `prices!vat` (a `named` node with its `table`), on another page `[[Page]]prices!vat`; so another table's cell needs that table named (nothing names it by itself: a name is metadata written into the table). A bare name of another table's cell, or `[[Page]]vat` (as formulas written before have them), is `#NAME?` saying how to write it (`namedElsewhere` in evaluate.ts, through `TableSource.cellsNamed`), and saving the formula writes it so (`qualifyCellNames` in autofix.ts, after the slip fixes) where one named table of the page has the name; nothing rewrites formulas not edited. Tables are recalculated for each other by table names only (`Affected`): a bare name is no reference to another table. While typing, the list offers the table's own cells bare, other named tables' as `table!name`, and after `table!` that table's cells alone. Names are the core's (it reads columns by them), written and read through host functions (`withColumnName`, `rowNames`…); the formulas get them through `FormulaCells`. A last row with one named empty cell is no metadata row: that is told by its `core.table`. Both names of a cell go in one tag. Names move with their cells, so references by name never need rewriting.
- **Custom functions** (the user's own) are JS, not Lua: a module of the space (`export default [ … ]`, or a function given HELPERS that returns the list), the built-in functions' form, given with `silverware.table.defineFunctions(js.importFromSpace(…))` in Space Lua. Lua was set aside: a Lua function called from JS returns a Promise as soon as it uses SilverBullet's standard library (`ipairs`, `table.insert`, `table.concat` did, verified), and formulas are calculated synchronously (on every view, in the write step); a Lua function would need results kept by arguments and waited for before writes. Verified: JS objects passed through Lua (and config) come back the same objects; `js.importFromSpace` gives the same module for the same path (the browser's module cache) and unwraps a sole default export. The API is a `-- priority: 50` block of the library page (the global `silverware.table`, as SilverBullet's `command.define` / `aggregate.define` APIs are blocks of high priority), so scripts of priority 0 can call it; each time Space Lua loads, the scripts' definitions replace those of before, which stay until the first of them (a write meanwhile, or a table shown, still has them; a function no script defines any more stays until a reload), and it imports the same module the main block inits. A mistake in a definition is a notification (SilverBullet's `error` has no level, so it would point at the library page, and it would stop the rest of the user's script). When definitions change (`tablesChanged`, not when a table renders anew: an edit does not change them), tables calling custom or unknown functions are checked again (`callsCustomFunctions`, the formulas module's recheck): one not defined keeps its result as written, Recalculate highlighted. A reference is passed to custom functions as to the built-in ones, a one-cell list for one cell. Names that read as a cell (`LOG2`, CELL_RE) or TRUE/FALSE are refused.
- Built-in functions live one per file in `formulas/builtin/` (only functions there: what they share is beside the folder); a test requires each one's syntax and description in the library page's Functions table. `call(args, context)`: the context is where the formula is calculated (`row`, `column`, as A1 counts), which `ROW()` uses and the others leave out; a result depends on the arguments and the context only. `ROW(reference)` is left out on purpose (in a spreadsheet it mostly works around what table-relative rows give here). *Insert numbered column left* (the formulas module's `columnMenuInsertEntries`, after *Move right*) adds a column `#` of `=ROW()`, a calculated column. There is no `INDEX` function.
- **Which functions are built in**: a function is added only when no existing function or the formula language already covers it (no VLOOKUP/HLOOKUP/MATCH/INDEX: XLOOKUP; no CONCATENATE: CONCAT and `&`; no SUMIF/COUNTIF/AVERAGEIF: the -IFS ones; no compatibility duplicates). Names are plain, without dots, with the modern behaviour: RANK is RANK.EQ, STDEV is STDEV.S, CEILING and FLOOR are CEILING.MATH and FLOOR.MATH (significance optional, its sign ignored), NETWORKDAYS and WORKDAY without .INTL. The -IFS conditions are Excel's (`criteria.ts`), not the filter row's syntax, so formulas copied from a spreadsheet work. Operators on ranges work cell by cell (`cellByCell` in evaluate.ts: a range and a value, or two ranges of the same size, give a range), so `TEXTJOIN(", ", TRUE, "**" & [name] & "**")` and `SUM([qty] * [price])` work as in Excel 365; functions taking one value (`IF`, `ROUND`) still take one, and a cell's result must be one value. No spilling, decided: spilled cells would be values in the markdown needing a mark of their source (else typed data gets overwritten), spilling lists of varying length (FILTER, SORT, UNIQUE) would add and remove rows among the records (sorting, filters, pins, references, undo), and Excel refuses spills in its tables too (#SPILL!). A value per row is a calculated column; a list is SilverBullet's query; a table generated whole from one formula in its metadata row was offered, not done. An argument left out between others (`XLOOKUP(a, b, c, , -1)`) is a null literal, which functions take as not given (a reference to an empty cell is a one-cell list, so it is told apart); a trailing one (`SUM(A1,)`) is not read, so autofix does not complete `=SUM(A1,` to it. Rounding functions take the noise of binary fractions off first (`tidy` in arguments.ts: 0.29 * 100 rounds down to 29); MOD, CEILING, FLOOR and MROUND of a time give a time (`MOD([@end] - [@start], 1)` for a shift past midnight).
- **Dates are ISO text** (`2025-11-06`, `2025-11-06 14:30[:15]`), not spreadsheet serial numbers: results are written into the markdown, and a serial number there would be unreadable, invisible to queries and not a `#date`. `formulas/dates.ts` reads and writes them on a clock without time zone (UTC arithmetic on the written fields); `+`/`-` with a date work as in a spreadsheet (days, date − date = days). Times of day are text too (`14:30`, what `TIME` gives, not a fraction of a day); date + time is the date at that time; the `#time` type also shows fractions of a day (pasted from spreadsheets). `TODAY()`/`NOW()` are written when calculated and show as stale (*Recalculate*) when out of date. The evaluator is synchronous; values are errors-as-values (`FormulaError`).
- Compared with MdTableSheet (malys): it locates a formula's table by searching the formula text in the index (fragile, stale until re-indexed, no chaining, results not visible elsewhere). Silverware Table evaluates from the markdown model it already has.

### Column types (`columntypes/`, `features/columntypes.ts`)
- A type is a **hashtag in the header** (`| Price #currency-usd |`), as MdTableRender does: verified not to change the column key nor tag rows or the page, needs no metadata setting, and MdTableRender's tables work (aliases: `#euro`, `#usd`, `#int`, `#float`, `#kg`, `#km`, `#watt`, `#logical`, `#evaluation`, `#gauge`). Parameters after a dash (`#number-2`, `#stars-10`, several dash-separated, the last taking the rest: `#unit-m-s`); MdTableRender's number suffixes (`#percent10`) are not supported. A type declares them (`params`: number with bounds, a choice of words, text with a pattern, each with an optional default) and the registry reads them (`readParams`): a hashtag whose parameters do not fit is not the type's, and the type's methods get the values (`format(text, { max })`, `columnType()` types them from the declaration), never the text after the dash.
- Display only: the markdown keeps the value; the editor shows it; what a type shows is a text, a link or a meter (`{ text, meter }`: the adapter draws a bar filled to the share with the text in a box in the page's colors over it, `swt-meter`; `#progress`), so the model side makes no element; sort/filter/copy use it (`sortValue` where the text does not sort, e.g. check marks). Invalid values show red with the reason; saving one is allowed and announced.
- The type is changed in the column menu (*Type*: a row of icons as *Filter*, the type's icon opens the list in the same dropdown, a back arrow before its title; the × removes it); editing a header shows and changes only the name, the type hashtag is kept.
- Built-in types live one per file in `columntypes/builtin/` (only types there); a test requires each type's syntax and description in the library page's Column types table. Each has an `icon` (`lineIcon` from `icons.ts`), shown after the column's name in the header and in the Type menu; the menu shows a type's syntax and description in a bubble beside it (`MenuDetail` in `menu.ts`), not a native tooltip.
- **Custom series** (AutoFill, `silverware.table.defineSeries`) are JS as custom functions are, the same API block and replacing on a reload of Space Lua; a definition is data (`words`, a list to go round, `alone: false` for words also used otherwise) or a series (`match`); tried before the built-in ones, as a user's words are meant to win (Q1 … Q4 round, not Q5). Nothing is rechecked when they change: a fill reads them when it starts.
- **Custom column types** are JS as custom functions are (`silverware.table.defineTypes`, the same priority-50 API block, the same replacing of definitions when Space Lua loads again, a mistake a notification), in the built-in types' form: they declare `params` and get their values, a name replacing a built-in type (in its place in the Type menu, its aliases gone with it), a type's own name before another's alias. A method that throws or gives the wrong kind of value (custom.ts checks what it gives) marks the cell `swt-type-invalid` with `#tag failed: …` (the column types module's `attempt`, around every call of a type's method), never breaking the table. Tables are decorated with the types when they render: SilverBullet loads Space Lua before it opens a page (and renders the editor anew after a reload of Space Lua), so the types are there; a change of definitions refreshes the CSS hiding type hashtags (`tablesChanged`), not cells already shown.

### Themes (`themes.ts`, `features/themes.ts`, the library page's CSS "Themes")
- A theme is CSS only: `--swt-*` variables on `.sb-table-widget[data-swt-theme="<name>"]`, and on `html[data-theme="dark"] …` for its dark look. SilverBullet decides light or dark (its own mode); the table has no mode of its own. A user's theme is a space-style block; it is found by its selector (`themesInStyles`), nothing is registered. Every variable is optional.
- The engine (library page CSS) turns the colors into SilverBullet's own variables within the table (`--editor-table-head-background-color`, `--editor-table-even-background-color`, `--editor-table-head-color`, `--ui-accent-color`), so SilverBullet's header and striping, the held header, pinned cells and the selection follow the theme without rules of their own; a variable left out falls back to the page's value captured on `html` (`--swt-sb-*`: a custom property cannot fall back to its own outer value). Lines, corners, shadow, padding and the header's type are rules of the engine. `:is(#sb-main, html)` gives them the weight of SilverBullet's `#sb-main .cm-editor …` table rules in SilverBullet and the playground alike. Fonts (`--swt-font`, `--swt-head-font`) are the device's (no web fonts loaded), declared without a fallback: left out, the declaration is invalid at computed-value time and the font is inherited. There is no table background of its own: --root-background-color stays the page's (it also fills the band above the held header).
- **Stripes are not the theme's**: a theme gives `--swt-stripe` (their color), the setting or the table chooses rows (SilverBullet's own striping), columns (every other body column, as a background image, pinned columns left out) or none, for any theme and native alike (rules keyed on `data-swt-stripes` only).
- **A theme's preview** in the Theme list: one small table for the list (`Themes.preview`), put into the menu's bubble by `MenuDetail.content` as an item shows its bubble, its `data-swt-theme` set to that item's. The theme rules key on `data-swt-theme` / `data-swt-stripes` alone (not `.swt-table`), so it is styled as the page's tables are; its base (padding, a bold header) is CSS of its own, as SilverBullet's own table rules are the editor's only. The core leaves tables in its floating elements alone (`ownTable`: not enhanced, not `tableAdded`).
- Choices found at run time: `Setting.moreChoices`/`moreLabel` and `settingChoices` (the dialog offers the user's themes and keeps a value no style defines); a toolbar ⋯ item's `choices` opens a list in the menu's place (made when it opens: finding themes reads every style rule).

### Other features
- **Select mode / Edit mode** (`features/selection.ts`): select mode is the default, as in a spreadsheet: a click selects a cell, a second click on the cell selected alone (or a double click) edits it, typing edits it with its text replaced, Enter/F2 edit it as it is, Backspace empties it. *Edit mode* (a toolbar icon left of ⋯, `aria-pressed`) edits on the first click. The mode is kept per browser in `localStorage` (`silverware.table.editMode`), not a setting. Select mode is `data-swt-select-mode` on `<html>` and a cell selected alone `swt-selected-alone`: CSS gives cells the default pointer there, the text cursor on the cell a click edits. Without the selection module, a click always edits. Tests: `useTablePage` turns edit mode on; select-mode tests remove the key.
- **Typing on a selected cell** opens the editor during the keydown without `preventDefault`, so the browser types the key into the field (dead keys and AltGr work; AltGr arrives as Ctrl+Alt). Ctrl+V on a selected cell opens its editor with the text selected, so the paste event lands in the field and the paste feature takes it (`Paste.keyDown` records Shift, as the key comes before the editor exists).
- **Selection** follows the rows as shown (sorted/filtered). Ctrl+Alt+arrows on a selection move its rows or columns as a block (`moveRowsTo`/`moveColumnsTo` in structure.ts, `moveRows`/`moveColumns`/`lineAfterBlockMove` in ops.ts; all in one zone of pins, else they stay), the selection mapped with them before the write (`enhanced` shows it again). Shift+click selects from the selection's first cell, else from the cell being edited (saved), else that cell. Keys on a selection: arrows / Ctrl+arrows move it, Home/End (row), Ctrl+Home/End (table), PageUp/PageDown (10 rows); with Shift they extend. Ctrl+Enter adds a row under the cell selected and edits it there, as in the editor (`ctrlEnterAddsRow`; off: the cell edited). Tab / Shift+Tab select the next / previous cell, on along the rows, Tab on the table's last cell adding a row and editing its first cell, as the editor's Tab does. In the editor, Enter on the last row shown adds a row (above those pinned to the bottom) and edits it, with the `moveDown` setting only. Esc in the cell editor drops the edit and leaves the cell selected; a second Esc ends that. *Click selects the cell's text* applies to Enter, Tab and Ctrl+arrows too; Shift+Enter is its reverse.
- **Deleting rows and columns**: Delete empties the selected cells (header names kept); on whole rows (all columns) or whole columns (header and every row shown) that are empty already, it deletes them, so a first Delete empties and a second deletes. The whole table so (its body empty in every row, hidden ones too): `TableHost.deleteTable(info, { unasked: true })`, asked only when something goes with it (`tableDeleteWarning`). Deleted, rows or columns (`deleteRowsAt`/`deleteColumnsAt`, whatever asked: Delete, the cell or grip menu) leave the line that took their place selected whole, through `selectCells` once written (`info.rows` counts the header); a table deleted on a grid, the frame's cell where it was (`AddressFrame.selectCell`). A column is deleted only if it is empty in every row, hidden rows included. *Delete N rows/columns* in the cell and grip menus; `deleteRowsAt`/`deleteColumnsAt` (one edit, pins adjusted, one question for names in all the columns).
- **Grips**: a click selects the row (column); in select mode (`host.clickSelects()`: the selection module's, generic) its menu opens with a second click on the line selected, a right click or a long press (550 ms, touch), in edit mode with the first click as before; the grip of a line selected is `swt-line-selected` (CSS: the context-menu pointer, not a text cursor: nothing is typed there); on a line of a whole-line selection the selection stays (menu: *Delete N rows*). Shift+click on a grip selects at once from the line a click selected (`lineAnchor`, while still selected; else the end of the lines or cells selected farther from it) to its line (no menu item to select lines: Shift+click, and the selection's handles on a touch screen).
- **Paste**: tab/line-break text (CSV-style quotes); Ctrl+V overwrites from the cell, adding rows/columns before the pinned ones; Ctrl+Shift+V inserts new rows; a cell a feature computes is left (`Feature.keepsCell`: formula cells); refused while sorted or filtered. New rows get calculated columns' formulas in the write step, where nothing was pasted.
- **Hidden tags in cells** (`tags.ts`): every `<meta …>` in a cell is kept when its text is edited, pasted over or cleared (`TableHost.keepTags`), whatever it is for; a feature that manages a tag's attributes takes them (`Feature.takesTags`, keys the core prefixes: formulas take `f`, `formulas.f`) and writes them itself. So a module turned off loses none of its data in cells. Their values are written in apostrophes, always (`metaAttribute` in markdown.ts, the one way to write an attribute: never `attr="…"` by hand): values are mostly formulas, whose texts are in quotes, so those stay as typed (`f='=IF(A1="x", 1, 2)'`); `'` is `&#39;`, `&` `&amp;`, `\` `&#92;`, `>` `&gt;`, `|` `\|`, always (no escaping only where needed). A tag ends at its first `>` as SilverBullet reads it, so the tags are found by one pattern that does the same (`TAG_BODY` / `metaTagPattern` in tags.ts; not a regex of its own). Readers take either quotes and `&quot;` / `&#39;` / `&apos;` / `&gt;`, as tables written before (2026-10-22) have quotes; such a tag stays as written until its cell is written for another reason (a recalculation compares results, not the cell's text, so an old table is not stale for its quotes).
- **Metadata removal** also removes formulas (cells keep their results) and ends a stored sort.
- **Functions while typing** (Excel's formula AutoComplete): `formulaChoices` (formulas/help.ts) lists the functions and the page's names (`nameChoices` in formulas/page.ts: named cells and tables of the page, named rows of the table edited, as written) whose names start with the name before the caret, ignoring case: a whole name first, the names before the functions; `choiceText` is what each inserts (`NAME(`, `row[`, `table!`, a cell's name). While the list shows, the formulas module takes ↑ ↓ Tab Esc in `editorKeyDown` (Esc closes it for that name, the editor stays). Enter is never the list's, as in Excel: it saves the formula as typed, so a name that also starts a function's (a cell `day`, DAY) needs no rule of its own. Tab on a name typed in full that inserts nothing (a cell's) moves on as elsewhere. The page's names are those of the page as last read (`pageNameChoices`, once per page's text), the rows the table's as edited (`rowNameChoices`): a name given in another cell meanwhile shows once that is saved. The hint lets presses through to the table (`pointer-events: none`) but the list takes them, and a press there does not end the editor (a panel is floating: `isFloating`). `formulaHelp` gives the function the caret is in and `argumentSpan` the argument in its syntax (past the arguments before "…", the repeating one). The *Functions* dialog (`features/functiondialog.ts`, Excel's Insert Function; fx in the hint, Shift+F3, *Insert function…* in the cell menu) finds them by name or description words (`findFunctions`) and group (`category`: math, logic, text, date, lookup; none: Custom) with each one's `example` (a test requires both on built-in functions, the example read by the parser); the one picked goes in place of the name typed at the caret (`nameTyped`), after a `+` where it would follow an operand (`needsOperator`, as Excel does), a text that is no formula yet starts one. A dialog rather than a panel by the cell: it needs room (search, groups, list, detail), and the list while typing already serves inline use.
- **Pointing** in formulas (click/drag cells, click header) uses the move cursor; only right after an operator, `(`, `,`, `=`, or replacing the reference just pointed at.
- **Pinned rows and columns** show a light tint of the accent color (`--swt-pinned-tint`, 12 %), not a border: a selected or edited cell draws its marks with inset shadows, which a border would clash with; a pinned column's edge has its shadow already.

### Excel (`excel/`, `features/excel.ts`)
- Its own module beside `export` (CSV): it has its own settings and grows its own code; both use `src/export/` (what a table gives), neither the other. Excel knows the formulas (their public API: the parsed tree, `totalRows`, references), the formulas know nothing of Excel: how each function is written in Excel is a table in `excel/functions.ts` by name, and a test there requires every built-in function in `SAME_IN_EXCEL` or `EXCEL_FUNCTIONS`, so a new function needs a decision. A function in neither (a custom one without a template) is written as its value.
- Formulas go into the .xlsx file only: pasted as text, Excel reads a formula in its UI's language (a Czech Excel wants SUMA and ;) and does not shift references to where it is pasted; a file keeps formulas in English, locale-independent. Copy for Excel copies values, typed with Excel's HTML attributes (x:num, x:bool, mso-number-format; "\@" keeps text text, so 1-2 is no date).
- The file has every row in the markdown's order (formulas refer to rows by place), the header at row 1, so A1 of a formula is Excel's A2; `[qty]` is one run of the column's rows without total rows (else the formula is its value); operators on ranges are array formulas (`t="array"`) so Excels before 365 calculate them. Results are written with the formulas (a reader that does not calculate shows them; their number formats come from Silverware Table's results: a date's result is a date) and `fullCalcOnLoad`. Functions newer than Excel 2007 are written with `_xlfn.` (else #NAME?). TEXT is written as its value: Excel reads its format codes in its own language.
- Verified by opening generated files with Excel (16.0, English UI) through COM: the file opens without repair, XLOOKUP / TEXTJOIN (array) / CEILING.MATH / EDATE / DATEDIF / WORKDAY calculate, dates, times ([h]:mm), percentages, logical values and errors show as written; and Copy for Excel from the playground in Chrome (Playwright, headed) pasted into Excel keeps its attributes (Chrome does not strip x:num nor mso-number-format) and gives numbers (12,99 € as 12.99) and text as meant. Not verified: Excel in another language, the download in SilverBullet's mobile app.
- What would break the file is never written: Excel refuses to open a whole file for one formula it cannot read (a wrong number of arguments, `SUM()`: verified), so a call outside its function's minArgs/maxArgs, an empty template or a range as the result is the cell's value, listed. A cell's text becomes a number only when nothing written is lost (`PLAIN_NUMBER_RE` in values.ts: `007`, a phone number, `3 kg`, more than 15 digits stay text). Templates are put in parentheses, their arguments that are operations too. The dialog groups formulas alike (a calculated column is one entry, its cells a range) and shows at most 50.

### Settings dialog
- One source with SilverBullet: it writes the Configuration Manager's managed block of CONFIG (Ctrl-, shows what it wrote and the reverse), every value changed written as it is, the default too (the value shown may come from another `config.set`, which the managed block, coming last, overrides).
- Modules on tabs by kind (each module declares its own: one tab of 21 modules was too long), each with its description and its own settings under it; a module turned on or off needs *Save and reload* (modules are created when Silverware Table starts). It says it is for every table in the space. Every setting has a `label` and a `hint`; the library page's `config.define` labels match them.

### Performance (large tables)
- Measured with the playground's benchmark and in SilverBullet (Chrome's trace: layouts and what forced them). After an edit SilverBullet renders the whole table anew and the browser lays it all out (an auto table layout depends on every row): that layout, paid once per change, is the cost; Silverware Table must not make the browser pay it more than once (no layout reads between writes in view hooks, controls placed in the next frame).
- **largeTables is off by default**: it changes how a large table looks (a box with its own scrollbar) and the browser's find sees only the rows in view. One setting, `minRows`: a row count, as a table's height would need the layout it avoids. The box is the one Maximum table height already makes (one scrollbar), else the window's height; virtualizing against the page's scroll (no box) was set aside: the table's height would be estimated, the page would move as rows are measured, and CodeMirror keeps a height map of its widgets.

## Maintainability: to revisit

Noted on 2026-10-22: small UI changes had started to take long. A first pass (the same day) took what features repeated into shared helpers of the core (`core/geometry.ts`, `press.ts`, `outline.ts`, `frame.ts`; `core/menu.ts` `floatingMenu`, `menu.ts` `namingThatCloses`; `TableHost.cellUnder` / `rowOf` / `heldBounds`), split the controller (2770 lines to about 1900: `modules.ts`, `core/rows.ts`, `anchor.ts`, `insert.ts`, `toolbar.ts`, `tablemenu.ts`) and added `npm run verify`. What is left:

**Shared helpers come first.** Before writing a feature's own version of something another feature does (geometry, taps, outlines, frames, menus, elements: `el` in elements.ts), look in `core/` and `menu.ts`; when two features need the same thing, it moves there, generic (the core knows no module).

1. **UI state across a table rendered anew.** Every write makes SilverBullet render the table again, asynchronously, and the core enhances it later. What is open at that moment (a menu, the selection, outlines, the Shift+click anchor, the cell editor, the view's anchor) must survive it, and each part does that its own way: `menuAgain` (grips), the view's anchor (`core/anchor.ts`), the selection shown again in `enhanced`, `pressTaken`, a right click waiting for `enhance`, `hoverWidget` replaced in `enhanceNow`. Most bugs of the last changes were here (a menu closed by the selection shown again, by `followScroll`/`hoverEnded` with a cell gone, a right click on a table not enhanced yet). Idea: one core mechanism: state keyed by the table's key and a cell's place (row/column in the markdown), not by DOM elements; the core restores it after `enhanced`, in a defined order, before features react (`selectionChanged`, `hoverEnded`). A feature registers "this is open, re-open it so" instead of guarding each event. Not done: the bugs it was meant for did not show in the playground (the toolbar and grips stay through edits: `silverware-table/ui-tests/rerender.spec.ts`, which fails with the hover not moved to the table rendered anew); what was done is the rule it rests on, in the grips: a menu reopens on its table's `enhanced` (not only when the selection module shows the selection again) and closes when the cells selected change, not when they are shown again (`selectionOf`). Follow that rule elsewhere: compare state keyed by table and cell, not events.
2. **Shared interaction state between modules.** Selection, hover, grip menus, the cell menu, picking modes (Move to…, AutoFill to…), `takePress`, `followScroll` all affect each other through events in the features' order. Idea: an explicit "interaction mode" in the core (idle, editing, menu open, picking, dragging) that features ask, instead of each one closing or keeping itself on events (`pointerBusy` is a start).
3. **Tests of interactions in jsdom.** jsdom has no layout: `followScroll`, `isShown`, `viewBounds` see everything at 0, so menus close in tests where a browser keeps them, and tests stub frames or mock `getBoundingClientRect` (flaky under load). Started: `silverware-table/ui-tests/` (Playwright against the playground, `npm run test:ui`, about 15 s) covers selecting, copy outlines, moving cells, AutoFill, the toolbar and menus, grips (menu, moving a row, its scroll), the +, a table rendered anew, a formula typed (its result, the tag as written, nothing of it shown once rendered from the page), touch (long press, tap, handles). A UI change gets its scenario there; jsdom stays for logic (markdown, formulas, ops, a feature's state), and its interaction tests that mock layout can move over as they are touched. Not done: CI.
4. **The cost of each change.** Per commit: review, fixes, a check in a browser, docs in two places (the library page and this file). Ideas: keep this file shorter (it repeats the code in prose; record decisions and verified facts, not what each function does); reviews batched for small changes. `npm run verify` checks the bundle now.
5. **Large files.** The controller is split (above); its view (sorting, the held row, placing rows, pinned columns) stays, as the playground's profiler measures its phases by name. `grips.ts` (row and column menus, dragging lines) and `selection.ts` (moving cells, touch handles) could be split the same way, each part behind the feature.
