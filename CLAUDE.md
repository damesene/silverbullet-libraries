# silverbullet-libraries: context for working on this repo

Libraries for [SilverBullet](https://silverbullet.md), installed straight from this repository. The main one is **Table Plus** (`table-plus/`): interactive markdown tables (in-place editing, sorting, filtering, rows and columns, pinning, formulas, column types, copy and paste with spreadsheets). The user-facing documentation is the library page [table-plus/table-plus.md](table-plus/table-plus.md); this file is the context behind it: how the code is built, what was verified about SilverBullet, and why things are the way they are.

## Commands

```
npm install
npm run build        # bundle table-plus/src/index.ts into table-plus/table-plus.js
npm test             # vitest (unit tests and jsdom UI tests)
npm run check        # tsc
npm run playground   # http://localhost:8000/: Table Plus without SilverBullet, on mock data
npm run deploy -- <space folder>   # copy the library into a local space
```

## Working rules

- **Rebuild before every commit**: `table-plus/table-plus.js` is committed, because SilverBullet installs it from the repo and runs no build. A commit with `src/` changes and a stale `.js` ships the old code. Nothing checks this automatically.
- **Commit messages**: one line, `Table Plus: <what changed>` (or `Playground: …`), no body, **no AI co-author trailer**. One feature or fix per commit.
- **Commit only when the user says so** ("commit"); until then changes stay in the working copy. Never push without being asked; never push to `main` directly unless asked. A change spanning several fixes is split into commits, each with `table-plus.js` built from its own changes.
- The conversation with the user is in Czech; everything in the repository (code, comments, docs, commit messages) is English.
- **A fix goes where it belongs**: the core gets generic mechanisms only (it knows no module by name, nor a module's classes or settings), a module's fix stays in the module. Features read rows through the host (`bodyRows`, `shownRows`, `cellAt`), never by querying the table's DOM.
- **What SilverBullet runs is not touched for the playground**: the benchmark measures from outside (playground/profile.ts wraps methods); no measuring, flags or checks for it in `src/`.
- Do not write files of a SilverBullet space on disk while SilverBullet has it open: it keeps its copy and writes a sync conflict into the page (it did, in CONFIG.md). Change pages through SilverBullet (its UI, a Table Plus command).
- Every commit: `npx tsc --noEmit`, `npx vitest run`, `npm run build` all pass. Run `npx tsc --noEmit --noUnusedLocals` too after moving code (tsconfig does not enforce it).
- Code style: match the surrounding code. Comments explain why, in full sentences or fragments; user-facing strings and docs are English. The library page is written for users: plain, specific, no internals.
- Line endings are LF (`.gitattributes`); editors on Windows may write CRLF into the working copy, git normalizes on commit.
- When editing files from a shell on this machine, heredocs mangle backslashes: write scripts to a file (or use an editor tool) when the text has `\`.

## Architecture

- **The controller is the host.** Features never touch its internals; they get a `TableHost` (`core/feature.ts`) and implement optional hooks: `start/stop`, `mouseDown` (any button, first), `beforeMouseDown`, `beforeCellPress` (true: taken, e.g. pointing), `afterCellPress`, `keyDown`, `enhanced`, `decorate`, `toolbarButtons`, `columnMenuEntries`, `cellHovered/hoverEnded`, `pointerBusy`, `owns`, `layoutChanged`, `beforeWrite`, and the editor hooks `editorText`, `editorOpened`, `editorKeyDown`, `editorValue`, `editorClosed`. Features get events in the order of the list in the controller's constructor (Sticky first, so the header moves before what points at it; ColumnTypes after Formulas, so formula results get formatted).
- **Every write is one `editor.replaceRange`** (one undo step): `write(widget, change, { focus, rowMap, columnMap, pins })` re-reads the table, applies `change`, then the **write steps** (the features' `writeStep` (formulas: calculated cells for new rows, references follow moved rows/columns, recalculation), then the core's `metadataAfterEdit`: every attribute of a column follows its column, pins), formats (autoFormat setting) and writes. `rowMap`/`columnMap` say where each row (markdown index, header 0) or column went; undefined means deleted. A row no old row maps to is new.
- **Viewing never writes.** Sorting and filtering are views unless the metadata setting stores them. Stale formula results are offered as *Recalculate*, not rewritten on view.
- **Sorting, filtering and copying use `cellValue(cell)`**: `data-tp-value` (set by column types) or the shown text.
- **Settings** (`bridge.ts` SETTINGS, `config.define` on the library page): whole-table settings are `tablePlus.<setting>`, a core part's `tablePlus.<part>.<setting>` (`editor`, `expressions`), a module's `tablePlus.modules.<module>.<setting>`, so a part is set with one `config.set("tablePlus.editor", { … })` and SilverBullet fills in the defaults left out. The modules (`FEATURE_NAMES`) can be turned off with `tablePlus.modules.<name>.enabled`; the controller reads these once when it starts and creates only the features that are on (a change applies on reload).
- **A module turned off is not loaded at all**: what it stored in tables stays and is not used (filters stored do not hide rows; with formulas off, results stay as written). The core knows no module: it offers generic mechanisms. Rows a feature hides (`hiddenRows`, `hidesRows` for "rearranged"); `columnsMoved` for state by column; `action` for clicks on a feature's `data-tp-action` elements in a table (clicks there reach the controller only); toolbar chips (`place: "chip"`); the cell menu (right click, long press, Menu key): `cellMenuEntries` in groups by `order`, `selectedCells` when the right click is in a selection. Attributes of columns in the metadata row, `<what>.<column>` (`sort.qty="desc"`, `filter.status="=open\|blocked"`, `qty:2` the second column of that name): `metadataAfterEdit` keeps every such attribute on its column through renames, moves and deletes whatever it is for (`followColumnMeta`), so data of a module turned off stays right. Writes: `prepareWrite`/`prepareEdit` (async, before the text is read and after the edit: pageLinks reads other pages), `writeStep`, `otherTablesWritten` (formulas: tables referring to the edited one, in the same edit). Other pages: the pageLinks module (which reads only while formulas are on: `host.moduleOn`) provides `otherPages()` (`host.otherPages()`), formulas read them through `formulas/page.ts` (`pageTables`; a page not read is `unread`, so formulas referring to it keep their results). Names: `columnDeleteWarning` (asked before deleting a column), `uniqueTags` (left out of a duplicated row). Remove metadata strips the metadata row and every hidden tag; `metadataPart` says what modules keep there, for the question.
- **The page's view** (`viewBounds`): CodeMirror's scroller (`.cm-scroller`, below SilverBullet's top bar), also while the page is too short to scroll (`scrollParentOf` then finds nothing, and the window's top would put the toolbar over the top bar), cut to the visual viewport (an on-screen keyboard). The cell editor is revealed again when the view resizes (window, `visualViewport`, `navigator.virtualKeyboard`; `core/touch-keyboard.ts`): on a phone SilverBullet (main) pins `#sb-root` to the area above the keyboard (`client/lib/keyboard_viewport.ts`; viewport meta `interactive-widget=resizes-content`).
- **A table written stays where it was in the view** (`anchorAt` in `write()`, `keepAnchor`/`anchorAgain` in `enhanceNow`): its top's offset in the scroller is restored once it is rendered anew, then after the cell to edit next is revealed, in the next frames and on the scroller's scroll events, for up to `ANCHOR_MS` or until the user wheels, touches, presses or types. The editor scrolled the page while it measured the new rendering (a long table scrolled down jumped).
- **Long text in cells**: the core's `layOutCells` (in `applyView`, so after any feature replaced a cell's content) puts each body cell's content into `div.tp-cell-content` (Table Plus' own elements, UI_CLASS, stay outside), an inline block as wide as its text: what modules size and limit. The longText module (`features/longtext.ts`, `tablePlus.modules.longText.{overflow, maxWidth, maxHeight}`) sets the limits (classes tp-long-text, which every rule of its CSS requires, tp-cells-wrap / tp-cells-ellipsis and CSS vars on the widget: wrapped up to the maximum height or cut with an ellipsis) and marks cells whose box is overflowed `tp-cut` (after layout, on window resize, a ResizeObserver on the tables, fonts loaded); off, cells are as SilverBullet shows them, and the expand button shows only for a field that does not fit (the popup and F2 are the cell editor's). A header is always on one line (`layOutHeaderCell` in dom.ts, last in `decorate`): `span.tp-head` (inline-flex, at most the maximum width; a width set by the widths module) holds the name (`.tp-head-name`, cut with an ellipsis) and Table Plus' inline icons after it (type, filter mark, sort), which always show; elements a feature marks `OUT_OF_LINE_CLASS` (positioned at the cell's edge: the pin mark, the width handle) stay in the cell; the core knows no module's element by name. The field of the cell editor is `CellField` (input | textarea): listeners on it go through `HTMLElement`, as the union loses the events' types.
- **The settings dialog** (`settings.ts`; *Table Plus settings…* in the ⋯ menu, the *Table Plus: Settings* command, `index.ts openSettings`): two tabs: *General* (groups of `SETTINGS` rows: `label` and `hint`, a switch, a choice from `choices`/`choiceLabels` or a number) and *Modules* (each module's `MODULE_LABELS` name, `MODULE_DESCRIPTIONS`, a switch, its own settings under it while it is on); `dialogKeys` (a test requires every setting in it); for every table (it says so). Its keys stay in it (the controller's key handler leaves them, Tab wraps, Esc asks where changes would be lost). It reads the configuration when it opens and changes nothing until Save: then `controller.saveSettings` writes what changed, each value as it is (the default too: the value shown may come from another `config.set`, which the managed block, coming last, overrides; a `readPage` failure other than a missing page writes nothing) with `bridge.saveSettings` (the playground's store) or into SilverBullet's CONFIG page, the Configuration Manager's managed block (`configpage.ts withConfigSettings`: only Table Plus' `config.set` lines, every other line kept, the block added or removed as needed; verified against `plugs/configuration-manager`), saved by the library page's Lua `saveConfigPage` as the Configuration Manager does (writePage, sync, index, `editor.reloadConfigAndCommands`). One source: Ctrl-, shows what the dialog wrote and the reverse. A module turned on or off: *Save and reload* (`bridge.reloadUI`, `editor.reloadUI`), as modules are created when Table Plus starts. Without a way to save (no `saveConfigPage`/`readPage` nor `saveSettings`) it only shows them.
- **Rows out of the document**: the core keeps each table's rows as SilverBullet rendered them (`rowsOf`, from its MutationObserver callback, before the browser lays the table out: `tableAdded` to the features), so `bodyRows`, `shownRows` (the display order the view last placed) and `cellAt` have every row whether it is in the document or not; features read rows through them, never `table.querySelectorAll("tr…")`, and do not measure a row out of the document (`isConnected`): `rowNeeded` puts it back first (the cell editor, the selection), `rowsAttached` tells them rows came back (longText checks their cut cells), `holdInDocument` keeps one there (a dragged row). A feature may place the shown body rows itself (`placeRows`): the largeTables module.
- **Large tables** (the playground's benchmark measures them): the browser's layout of a table of thousands of cells is the cost to avoid paying more than once per change. Hooks that run on every view (`decorate`, `viewApplied`, `toolbarButtons`) touch only the cells they change (no style reset on every cell), read layout or computed styles before writing, not between writes, and measure nothing that can wait: the toolbar is built at once but placed in the next frame after a change (`placeBar`). `parseTable` keeps the last tables parsed (they are immutable), so parts reading `info.source` again cost nothing; column types share their `Intl` formatters (`columntypes/format.ts`).
- **Rendered tables are SilverBullet's.** Table Plus decorates the DOM SilverBullet rendered and matches it to the markdown by position (`data-pos`) and shape. Everything assumed about SilverBullet's DOM lives in `dom.ts`.
- **Selecting and editing through the host**: `selectCells`/`selectedCells`/`selectsCells` (a feature that selects: the selection module), `editCell(info, ref, "replace" | "select")` (open a cell's editor from the keyboard), `saveEditing` (close the editor saving, as leaving it does: what a feature holds stays held), `takeEditor` (close the editor, its value saved in the write the caller makes: a paste). The editor knows no selection: Esc and Ctrl+Shift+arrows call `selectCells` when `selectsCells()`.
- **Edits held instead of written** (the lazy module): the cell editor asks `holdCellEdit` before writing a body cell (a header's name is written at once); a feature that holds edits gives them through `pendingEdits(info)` (`apply` to a table, `written` once in the page). `write()` applies them to the table it read before its change, so any write takes them along and rows and columns stay in step; `tableOf(info)` is the table with them (what the cell editor starts from). `pageLoaded` (the library page's `editor:pageLoaded` listener, `index.ts pageLoaded`): another page is in the editor, so what was held for the page left goes into its file, never into the editor.
- **Floating controls** (toolbar, grips, the +, menus) are `.tp-floating` elements in `body`, shown with `.tp-visible`. Hidden with `display: none !important`: themes set `display` on every `button` with `!important` (e.g. Tiniri), which left grips and the + stuck in view.
- **The + on borders** (controller: `showInsert`, `insertAt`, `inInsertBand`): shown for mouse and pen hover in a band left of the table / above the header (in a lane of its own beside the grips, left of the row grips or above the column grips, on the border nearest the pointer, none over a grip: `INSERT_LANE_*`; the toolbar keeps `BAR_CLEAR` left of the table's right edge, clear of the + there); quiet + buttons under the last row and right of the last column (`quietMarks`, `tp-quiet`, lit up under the pointer) show while a cell of it is edited, hovered or selected (`quietTarget`; hovers go through `cellHovered`, the selection module calls `selectionChanged`), also with the pointer away from the table, and give way to a + the pointer brings up on the same axis; a press on the + or in that band is taken on `mousedown` (it inserts if a + shows), because SilverBullet's table widget moves the cursor into the table on a click (markdown shown). The `mouseup`/`click` ending a press that inserted is swallowed (`insertPressAt`): the table rendered anew puts something else under the pointer (a link it would follow). Rows and columns scrolled under what is held over them (the header held at the top, pinned rows and columns: `heldBounds`) get no grip, their borders no +: the floating controls are in `body`, so CSS cannot put the held header over them. Recomputed under the pointer when the page scrolls (`insertUnderPointer`), hidden when the pointer leaves the window. While a grip menu is open (`pointerBusy() === "menu"`) the grips keep following the pointer in that table and no + shows.

## What was verified in SilverBullet (by probe pages)

Probes were pages with a test table and a one-line Lua expression listing the index, e.g.
`${(function() local p = editor.getCurrentPage() local out = {} for _, row in ipairs(query[[from index.tag "table" where page == p order by pos]]) do … end … end)()}`.
A new `space-lua` block on a page is not active until Space Lua is reloaded; an inline `${(function() … end)()}` needs no reload.

- **Column keys** in the index: `cleanHeaderFieldName` in `plugs/index/table.ts`: `str.replace(/[\W_]+/g, "_").toLowerCase()`, where `\W` is ASCII-only, so letters with diacritics become `_` (`Množství` → `mno_stv_`). **Hashtags in a header are left out** (`Price #euro` → `price`, `#stars Rating` → `rating`). `columns.ts` mirrors both.
- **Hashtags in a header tag neither the rows (`tags` stays empty) nor the page** (no tag objects).
- **Hashtags render** as `<a class="hashtag sb-hashtag" data-tag-name="…" data-ref="…">#…</a>` (`client/markdown_renderer/markdown_render.ts`).
- **`<meta …>` in a table cell is not shown** (any position, self-closing, single quotes, with `\|`); an HTML comment *is* shown. The index stores the **raw cell text** including the `<meta>` tag, with `\|` still escaped.
- **Empty cells** are indexed with an empty value (the key is present).
- MdTableRender hides header hashtags with JS (`display: none`), which flickered while tables rendered; Table Plus hides type hashtags with CSS injected at load.
- **On a phone SilverBullet scrolls to its editor's cursor** whenever its editor counts as focused (`contentDOM.contains(document.activeElement)`, true for a cell editor's field, which is in the content) and the on-screen keyboard shows or goes or the focus moves (`client/components/keyboard_bar.tsx`, seen in a log on Android: CodeMirror's `scrollRectIntoView` setting the scroller's `scrollTop`). SilverBullet also focuses its editor when a page opens. So Table Plus takes the editor's focus on a touch in a table, does not hand it back after a touch, and scrolls the cell being edited back for a moment after its editor opens or the view resizes (ended by a touch, wheel or press). All of it is in `core/touch-keyboard.ts`, kept apart as a workaround, to go once SilverBullet behaves otherwise.
- **A click on a table widget shows its markdown**: `client/codemirror/syntax/table.ts` listens for `click` on the widget and dispatches a selection at the target's `data-pos` (else the widget's start). Any click that reaches the widget (not stopped by the controller's capture handlers) opens the markdown.

## Design decisions (and why)

### Formulas (`formulas/`, `features/formulas.ts`)
- Stored in the cell as the **result plus a hidden `<meta f="=…">`**: every renderer and the index see a value; `<meta>` is invisible (verified). Chosen over storing formulas in the metadata row, because a formula addressed by cell position there could, after an edit outside Table Plus, overwrite a value typed by hand.
- **New formulas need the Store table metadata setting** (they are metadata); with it off a typed formula is saved as text, existing ones keep working (also as calculated columns).
- References: `A1` = first body row (header not counted, as MdTableSheet does), ranges, `[name]` (whole column, without cells whose formulas refer to that whole column: totals), `[@name]` (this row), `[name:2]` for duplicate names. Column references are written by **SilverBullet's column key** (`[unit_price]`), the same key a query uses; any spelling with the same key matches.
- Edits made with Table Plus shift references (rows/columns inserted, deleted, moved, sorted into the markdown, columns renamed); `#REF!` for deleted cells. Edits made in the markdown do not.
- **Other tables**: a table is named in its metadata row (`<meta name="prices">`, *Name* in the toolbar, rules in `meta.ts`). Formulas refer to it as `prices!B2`, `prices![price]`, or on another page `[[Page]]prices!B2` (tokens of kind `table`). The evaluator gets a `TableSource` (name, page → Table); a `Book` makes one `Sheet` per table, so other tables' formulas are evaluated too and cycles across tables are `#CYCLE!`. The formulas module builds the source from the page text (`formulas/page.ts` `pageTables`); the pageLinks module caches other pages read with `space.readPage` (re-read for every write that recalculates a table referring to them, and when SilverBullet indexes that page). A write recalculates, in the same edit, the tables that refer to the edited one by name (transitively); their references follow its moved rows/columns, renamed columns and new name (`followTable`). References from other pages do not follow. A page not read (the `pageLinks` module off, or not read yet): `TableSource.unread` makes formulas referring to it keep their stored results (`Book.keepsResult`; an empty one or an error code is an error). `[col]` leaves out the table's total rows (a cell that refers to its own whole column), so columns of a table line up for `XLOOKUP`.
- **Names in cells** (`names.ts`, `features/names.ts`): one hidden tag in a cell, `<meta n="…" cn="…">`, kept by the cell editor, paste and Delete. `n` names the line the cell heads: in a header the column's name, apart from its header text (*Name column*; `columns.ts` finds it first, `columnIdOf` writes it, so references and the stored sort use it whatever the header says; verified that SilverBullet leaves `<meta>` out of the column key). In a body cell `n` is the row's name (`pear[price]`, in the first cell or wherever a column move took it; unique in the table), and `cn` names the cell for formulas (`vat`, `[[Page]]vat`; own table first, then the page via `TableSource.cell`), unique on the page. Attributes `n`/`cn`, not `name`: a last row with one named empty cell must not read as the table's metadata row (`parseMetaRow` leaves out rows with `f`, `n` or `cn`). Both names of a cell go in one tag. Names move with their cells, so references by name never need rewriting.
- **Custom functions** (the user's own) are JS, not Lua: a module of the space (`export default [ … ]`, or a function given HELPERS that returns the list), the built-in functions' form, given with `tablePlus.defineFunctions(js.importFromSpace(…))` in Space Lua. Lua was set aside: a Lua function called from JS returns a Promise as soon as it uses SilverBullet's standard library (`ipairs`, `table.insert`, `table.concat` did, verified), and formulas are calculated synchronously (on every view, in the write step); a Lua function would need results kept by arguments and waited for before writes. Verified: JS objects passed through Lua (and config) come back the same objects; `js.importFromSpace` gives the same module for the same path (the browser's module cache) and unwraps a sole default export. The API is a `-- priority: 50` block of the library page (the global `tablePlus`, as SilverBullet's `command.define` / `aggregate.define` APIs are blocks of high priority), so scripts of priority 0 can call it; each time Space Lua loads, the scripts' definitions replace those of before, which stay until the first of them (a write meanwhile, or a table shown, still has them; a function no script defines any more stays until a reload), and it imports the same module the main block inits. A mistake in a definition is a notification (SilverBullet's `error` has no level, so it would point at the library page, and it would stop the rest of the user's script). When definitions change (`tablesChanged`, not when a table renders anew: an edit does not change them), tables calling custom or unknown functions are checked again (`callsCustomFunctions`, the formulas module's recheck): one not defined keeps its result as written, Recalculate highlighted. A reference is passed to custom functions as to the built-in ones, a one-cell list for one cell. Names that read as a cell (`LOG2`, CELL_RE) or TRUE/FALSE are refused.
- Built-in functions live one per file in `formulas/builtin/` (only functions there: what they share is beside the folder); a test requires each one's syntax and description in the library page's Functions table. `call(args, context)`: the context is where the formula is calculated (`row`, `column`, as A1 counts), which `ROW()` uses and the others leave out; a result depends on the arguments and the context only. `ROW(reference)` is left out on purpose (in a spreadsheet it mostly works around what table-relative rows give here). *Insert numbered column left* (the formulas module's `columnMenuInsertEntries`, after *Move right*) adds a column `#` of `=ROW()`, a calculated column. There is no `INDEX` function.
- **Dates are ISO text** (`2025-11-06`, `2025-11-06 14:30[:15]`), not spreadsheet serial numbers: results are written into the markdown, and a serial number there would be unreadable, invisible to queries and not a `#date`. `formulas/dates.ts` reads and writes them on a clock without time zone (UTC arithmetic on the written fields); `+`/`-` with a date work as in a spreadsheet (days, date − date = days). Times of day are text too (`14:30`, what `TIME` gives, not a fraction of a day); date + time is the date at that time; the `#time` type also shows fractions of a day (pasted from spreadsheets). `TODAY()`/`NOW()` are written when calculated and show as stale (*Recalculate*) when out of date. The evaluator is synchronous; values are errors-as-values (`FormulaError`).
- Compared with MdTableSheet (malys): it locates a formula's table by searching the formula text in the index (fragile, stale until re-indexed, no chaining, results not visible elsewhere). Table Plus evaluates from the markdown model it already has.

### Column types (`columntypes/`, `features/columntypes.ts`)
- A type is a **hashtag in the header** (`| Price #currency-usd |`), as MdTableRender does: verified not to change the column key nor tag rows or the page, needs no metadata setting, and MdTableRender's tables work (aliases: `#euro`, `#usd`, `#int`, `#float`, `#kg`, `#km`, `#watt`, `#logical`, `#evaluation`, `#gauge`). Parameters after a dash (`#number-2`, `#stars-10`); MdTableRender's number suffixes (`#percent10`) are not supported.
- Display only: the markdown keeps the value; the editor shows it; sort/filter/copy use it (`sortValue` where the text does not sort, e.g. check marks). Invalid values show red with the reason; saving one is allowed and announced.
- The type is changed in the column menu (*Type* → list in the same dropdown, a back arrow before its title); editing a header shows and changes only the name, the type hashtag is kept.
- Built-in types live one per file in `columntypes/builtin/` (only types there); a test requires each type's syntax and description in the library page's Column types table. Each has an `icon` (`lineIcon` from `icons.ts`), shown after the column's name in the header and in the Type menu; the menu shows a type's syntax and description in a bubble beside it (`MenuDetail` in `menu.ts`), not a native tooltip.

### Themes (`themes.ts`, `features/themes.ts`, the library page's CSS "Themes")
- A theme is CSS only: `--tp-*` variables on `.sb-table-widget[data-tp-theme="<name>"]`, and on `html[data-theme="dark"] …` for its dark look. SilverBullet decides light or dark (its own mode); the table has no mode of its own. A user's theme is a space-style block; it is found by its selector (`themesInStyles`), nothing is registered. Every variable is optional.
- The engine (library page CSS) turns the colors into SilverBullet's own variables within the table (`--editor-table-head-background-color`, `--editor-table-even-background-color`, `--editor-table-head-color`, `--ui-accent-color`), so SilverBullet's header and striping, the held header, pinned cells and the selection follow the theme without rules of their own; a variable left out falls back to the page's value captured on `html` (`--tp-sb-*`: a custom property cannot fall back to its own outer value). Lines, corners, shadow, padding and the header's type are rules of the engine. `:is(#sb-main, html)` gives them the weight of SilverBullet's `#sb-main .cm-editor …` table rules in SilverBullet and the playground alike. Fonts (`--tp-font`, `--tp-head-font`) are the device's (no web fonts loaded), declared without a fallback: left out, the declaration is invalid at computed-value time and the font is inherited. There is no table background of its own: --root-background-color stays the page's (it also fills the band above the held header).
- **Stripes are not the theme's**: a theme gives `--tp-stripe` (their color), the setting or the table chooses rows (SilverBullet's own striping), columns (every other body column, as a background image, pinned columns left out) or none, for any theme and native alike (rules keyed on `data-tp-stripes` only).
- **A theme's preview** in the Theme list: one small table for the list (`Themes.preview`), put into the menu's bubble by `MenuDetail.content` as an item shows its bubble, its `data-tp-theme` set to that item's. The theme rules key on `data-tp-theme` / `data-tp-stripes` alone (not `.tp-table`), so it is styled as the page's tables are; its base (padding, a bold header) is CSS of its own, as SilverBullet's own table rules are the editor's only. The core leaves tables in its floating elements alone (`ownTable`: not enhanced, not `tableAdded`).
- Choices found at run time: `Setting.moreChoices`/`moreLabel` and `settingChoices` (the dialog and the playground offer the user's themes and keep a value no style defines); a toolbar ⋯ item's `choices` opens a list in the menu's place (made when it opens: finding themes reads every style rule).

### Other features
- **Select mode / Edit mode** (`features/selection.ts`): select mode is the default, as in a spreadsheet: a click selects a cell, a second click on the cell selected alone (or a double click) edits it, typing edits it with its text replaced, Enter/F2 edit it as it is, Backspace empties it. *Edit mode* (a toolbar icon left of ⋯, `aria-pressed`) edits on the first click. The mode is kept per browser in `localStorage` (`tablePlus.editMode`), not a setting. Without the selection module, a click always edits. Tests: `useTablePage` turns edit mode on; select-mode tests remove the key.
- **Typing on a selected cell** opens the editor during the keydown without `preventDefault`, so the browser types the key into the field (dead keys and AltGr work; AltGr arrives as Ctrl+Alt). Ctrl+V on a selected cell opens its editor with the text selected, so the paste event lands in the field and the paste feature takes it (`Paste.keyDown` records Shift, as the key comes before the editor exists).
- **Selection** follows the rows as shown (sorted/filtered). Ctrl+Alt+arrows on a selection move its rows or columns as a block (`moveRowsTo`/`moveColumnsTo` in structure.ts, `moveRows`/`moveColumns`/`lineAfterBlockMove` in ops.ts; all in one zone of pins, else they stay), the selection mapped with them before the write (`enhanced` shows it again). Shift+click selects from the selection's first cell, else from the cell being edited (saved), else that cell. Keys on a selection: arrows / Ctrl+arrows move it, Home/End (row), Ctrl+Home/End (table), PageUp/PageDown (10 rows); with Shift they extend. Esc in the cell editor drops the edit and leaves the cell selected; a second Esc ends that. *Click selects the cell's text* applies to Enter, Tab and Ctrl+arrows too; Shift+Enter is its reverse.
- **Deleting rows and columns**: Delete empties the selected cells (header names kept); on whole rows (all columns) or whole columns (header and every row shown) that are empty already, it deletes them, so a first Delete empties and a second deletes. A column is deleted only if it is empty in every row, hidden rows included. *Delete N rows/columns* in the cell and grip menus; `deleteRowsAt`/`deleteColumnsAt` (one edit, pins adjusted, one question for names in all the columns).
- **Grips**: a click selects the row (column) and opens its menu; on a line of a whole-line selection the selection stays (menu: *Delete N rows*). Shift+click on a grip and *Select rows/columns* start picking: the pointer moves the other end, a click in the table ends it (taken, no editor), Esc keeps the first line.
- **Paste**: tab/line-break text (CSV-style quotes); Ctrl+V overwrites from the cell, adding rows/columns before the pinned ones; Ctrl+Shift+V inserts new rows; a cell a feature computes is left (`Feature.keepsCell`: formula cells); refused while sorted or filtered. New rows get calculated columns' formulas in the write step, where nothing was pasted.
- **Hidden tags in cells** (`tags.ts`): every `<meta …>` in a cell is kept when its text is edited, pasted over or cleared (`TableHost.keepTags`), whatever it is for; a feature that manages a tag's attributes takes them (`Feature.takesTags`: formulas take `f`) and writes them itself. So a module turned off loses none of its data in cells.
- **Metadata removal** also removes formulas (cells keep their results) and ends a stored sort.
- **Pointing** in formulas (click/drag cells, click header) uses the move cursor; only right after an operator, `(`, `,`, `=`, or replacing the reference just pointed at.
- **Pinned rows and columns** show a light tint of the accent color (`--tp-pinned-tint`, 12 %), not a border: a selected or edited cell draws its marks with inset shadows, which a border would clash with; a pinned column's edge has its shadow already.

### Settings dialog
- One source with SilverBullet: it writes the Configuration Manager's managed block of CONFIG (Ctrl-, shows what it wrote and the reverse), every value changed written as it is, the default too (the value shown may come from another `config.set`, which the managed block, coming last, overrides).
- Modules on their own tab, each with its description and its own settings under it; a module turned on or off needs *Save and reload* (modules are created when Table Plus starts). It says it is for every table in the space. Every setting has a `label` and a `hint`; the library page's `config.define` labels match them.

### Performance (large tables)
- Measured with the playground's benchmark and in SilverBullet (Chrome's trace: layouts and what forced them). After an edit SilverBullet renders the whole table anew and the browser lays it all out (an auto table layout depends on every row): that layout, paid once per change, is the cost; Table Plus must not make the browser pay it more than once (no layout reads between writes in view hooks, controls placed in the next frame).
- **largeTables is off by default**: it changes how a large table looks (a box with its own scrollbar) and the browser's find sees only the rows in view. One setting, `minRows`: a row count, as a table's height would need the layout it avoids. The box is the one Maximum table height already makes (one scrollbar), else the window's height; virtualizing against the page's scroll (no box) was set aside: the table's height would be estimated, the page would move as rows are measured, and CodeMirror keeps a height map of its widgets.

## Deferred / open

- **Custom column types** (as custom functions are: a JS module given from Space Lua), next. Lua functions for formulas (results kept by arguments, waited for before writes; also the value of a `${…}` cell for formulas) were offered, not done.
- A parameter picker for column types in the menu (today only the base form is offered; parameters are typed in the markdown).
- A check that `table-plus.js` matches `src/` (`npm run check-build` or a pre-commit hook).
- The band of the + could be found without hovering the table first (coming from the left or below, no + shows and a press there reaches SilverBullet). Offered, not done.
- Enter after editing in select mode follows `enterKey` (edits the cell below); a spreadsheet would only select it.
- Tests run in jsdom (layout is mocked where needed). Agents check UI with Playwright in the playground and in a local SilverBullet (a container of the latest release, the library deployed with `npm run deploy`); the user's deployed SilverBullet (Docker, latest release, the Tiniri theme) can differ.
- **Enter without rewriting the table** (offered, not done): Enter would show the value and open the next cell at once, the markdown written in one go after a pause or when the table is left; each Enter then costs milliseconds. Costs: formulas, totals and sorting update after the pause, Ctrl+Z undoes the batch, edits held in memory for a moment.
- **Recalculating only the formulas an edit affects** (offered, not done): today every write recalculates the whole table (`formulas · writeStep`, the largest part of an edit after the layout).
- largeTables: the browser's find (Ctrl+F) sees only the rows in view; columns' widths are kept from the first rows shown (they only grow); the height of rows out of view is estimated, so the scrollbar may jump a little with rows of different heights.
